What Are AES Modes of Operation?

The Advanced Encryption Standard (AES) is a symmetric-key block cipher that processes data in fixed 128-bit blocks. A mode of operation defines how AES is applied repeatedly to encrypt data longer than one block.

Choosing the right mode is critical — it affects confidentiality, integrity, parallelism, error propagation, and throughput. This analysis compares the six most widely-used modes.

Modes of Operation

Click any card to learn more about each mode.

Insecure

ECB

Electronic Codebook

P₁ → [AES_K] → C₁
P₂ → [AES_K] → C₂
P₃ → [AES_K] → C₃

Each block is encrypted independently with the same key. Identical plaintext blocks produce identical ciphertext blocks, leaking patterns.

  • ✓ Parallelizable (encrypt & decrypt)
  • ✓ No IV required
  • ✗ Leaks plaintext patterns
  • ✗ No diffusion across blocks
Legacy

CBC

Cipher Block Chaining

C₁ = AES_K(P₁ ⊕ IV)
C₂ = AES_K(P₂ ⊕ C₁)
C₃ = AES_K(P₃ ⊕ C₂)

Each plaintext block is XORed with the previous ciphertext block before encryption. Requires an unpredictable IV and padding.

  • ✓ Hides plaintext patterns
  • ✓ Decrypt is parallelizable
  • ✗ Encrypt is sequential
  • ✗ Vulnerable to padding oracle
Stream

CFB

Cipher Feedback

C₁ = P₁ ⊕ AES_K(IV)
C₂ = P₂ ⊕ AES_K(C₁)
C₃ = P₃ ⊕ AES_K(C₂)

Turns AES into a self-synchronizing stream cipher. Uses only the encryption function for both directions. No padding needed.

  • ✓ No padding required
  • ✓ Decrypt is parallelizable
  • ✗ Encrypt is sequential
  • ✗ Error propagation (1 + fraction)
Stream

OFB

Output Feedback

O₁ = AES_K(IV);  C₁ = P₁ ⊕ O₁
O₂ = AES_K(O₁); C₂ = P₂ ⊕ O₂
O₃ = AES_K(O₂); C₃ = P₃ ⊕ O₃

Generates a keystream independent of plaintext. A single bit error in ciphertext affects only the corresponding plaintext bit.

  • ✓ No error propagation
  • ✓ No padding required
  • ✗ Fully sequential
  • ✗ Keystream must never repeat
Recommended

CTR

Counter Mode

C₁ = P₁ ⊕ AES_K(Nonce‖1)
C₂ = P₂ ⊕ AES_K(Nonce‖2)
C₃ = P₃ ⊕ AES_K(Nonce‖3)

Encrypts a counter value to produce a keystream. Fully parallelizable, random access, and no padding — an excellent building block.

  • ✓ Fully parallelizable
  • ✓ Random access to blocks
  • ✓ No padding required
  • ✗ Nonce reuse is catastrophic
Best Practice

GCM

Galois/Counter Mode

CTR encryption + GHASH auth
Provides AEAD: confidentiality
+ integrity + authenticity

Combines CTR-mode encryption with Galois-field multiplication for authentication. The gold standard for authenticated encryption.

  • ✓ Authenticated encryption (AEAD)
  • ✓ Fully parallelizable
  • ✓ Hardware-accelerated (GCM-SIV)
  • ✗ Nonce reuse breaks auth & conf.

Performance Analysis

Relative throughput measured on a modern x86-64 CPU with AES-NI. Higher is better.

🚀 Parallelism Wins

CTR and GCM can process multiple blocks simultaneously using AES-NI pipelining, achieving up to 4–6 GB/s on a single core. ECB shares this property but lacks security.

🔗 Sequential Bottleneck

CBC, CFB, and OFB encryption must complete one block before starting the next, limiting throughput to ~2–3 GB/s despite hardware acceleration.

🛡️ Auth Overhead

GCM adds a GHASH computation for authentication, costing roughly 5–10% throughput compared to raw CTR. Hardware CLMUL instructions minimize this cost.

Security Analysis

CRITICAL

ECB Pattern Leakage

Identical plaintext blocks always map to identical ciphertext blocks. This reveals structure in the plaintext — famously demonstrated with the "ECB Penguin" image.

Impact: Confidentiality completely broken for structured data.
HIGH

CBC Padding Oracle

If an attacker can distinguish valid from invalid padding, they can decrypt the entire message byte-by-byte. Attacks like POODLE and Lucky13 exploited this in TLS.

Impact: Full plaintext recovery without the key.
HIGH

Nonce Reuse (CTR / GCM)

Reusing a nonce with the same key produces the same keystream. XORing two ciphertexts yields the XOR of the two plaintexts, enabling cryptanalysis. In GCM, it also leaks the auth key.

Impact: Confidentiality loss; in GCM, authentication forgery.
MEDIUM

Bit-Flipping (CTR / OFB / CFB)

Stream-cipher modes are malleable — flipping a ciphertext bit flips the corresponding plaintext bit. Without a MAC, an attacker can modify messages predictably.

Impact: Targeted plaintext modification without detection.
MEDIUM

Birthday Bound (64-bit modes)

After encrypting 232 blocks (~68 GB) with a single key, block collisions become likely. GCM's 96-bit nonce limits it to 232 invocations per key.

Impact: Distinguishing attacks; key rotation required.
LOW

Lack of Authentication

ECB, CBC, CFB, OFB, and CTR provide confidentiality only. Without a separate MAC (e.g., HMAC), tampered ciphertexts are accepted silently.

Impact: No tamper detection; must pair with HMAC.

Recommendations

✅ Do

  • Use AES-256-GCM as your default choice
  • Generate nonces with a CSPRNG or use a counter
  • Rotate keys before the birthday bound (~232 messages)
  • Use constant-time comparison for authentication tags
  • Consider AES-GCM-SIV if nonce misuse is a risk

❌ Don't

  • Never use ECB for anything beyond single-block values
  • Avoid CBC in new designs — padding oracles are hard to prevent
  • Never reuse a nonce with the same key in CTR or GCM
  • Don't encrypt without authenticating — always use AEAD or add HMAC
  • Don't implement your own crypto primitives

📋 Use-Case Guide

  • Network traffic (TLS): AES-GCM
  • Disk encryption: AES-XTS
  • Database fields: AES-GCM / AES-GCM-SIV
  • File encryption: AES-GCM with chunking
  • Legacy systems: AES-CBC + HMAC (Encrypt-then-MAC)
